## Reproduction and root cause
- **Q-04 backend gap (reproduced).** `/jobs/app/stream` (the app-wide Jobs stream) hand-rolled its `send` and, in its `catch`, only called `console.error`. Its two siblings (`/projects/:slug/jobs/stream`, `/jobs/all/stream`) use `createBufferedJobStream` and call `sendSnapshotError()`. So a failed app snapshot never reached the client's `snapshot-error` listener (`useAllJobs.ts:171`) and the view rendered an incomplete list as if complete. The same route also registered its update listeners before reading the snapshot, so an update could overtake it — the ordering the buffered helper exists to prevent.
- **Q-04 client fallback (already documented, kept).** `useJobs.startFallbackPolling` is one-way after `MAX_STREAM_FAILURES`: polling still converges to fresh state every 10s, stale responses are guarded by `transportEpoch`/`stateRevision`, and the header documents the fallback. Per the packet ("do not impose a reconnect redesign if the current fallback is correct and documented"), no reconnect change was made.
- **E-11 (reproduced).** `jobs.vue` declared `queuePaused = ref(false)` and `checkQueuePaused`'s `catch` kept the last value, so an unreadable `/system/queue/status` rendered the queue as **running** — AGENTS.md §6 ("could not work out the answer" must not share a value with "the answer is none").
- RED evidence for E-11: the new static guard (`jobsQueueVisibility.test.ts`) asserted `ref<boolean | null>(null)` and `catch { queuePaused.value = null }`, neither of which existed pre-fix. RED evidence for the route: the new guard asserted `createBufferedJobStream(send, 'Could not load Jobs.')` and `sendSnapshotError()` in the app route, neither of which existed pre-fix. Both were written against the fixed source and fail against the pre-fix source by construction; the behavioural half (`createBufferedJobStream` emits one `snapshot-error` before releasing buffered updates) was already pinned in `jobs-stream.test.ts:55`.
