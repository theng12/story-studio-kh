## Reproduction and root cause
- Exact steps/fixture and expected versus actual behavior:
  1. `useTempDataDir()` sets an isolated data dir; **no** GenStudio key is stored.
  2. A disposable project gets a `jobs.json` containing one persisted `running` audio job with a durable provider identity (`genstudio_jobs: [{ id: 'provider-1', operation: 'voice.tts', state: 'accepted' }]`) and a pending cancellation record (`remote_cancellations['voice.tts:provider-1'].status = 'queued'`).
  3. `getJobs(project)` loads it through the real recovery path, which sets `local_execution_complete = true` and schedules `reconcileCancellationJob`.
  4. With no key, the branch reads the key, appends `Cancellation is waiting for the GenStudio API key to be available on this Mac.`, persists, emits, and returns; the `finally` reschedules the pass in 5s while the job is still `running` and `requiresCancellationReconciliation` is true.
  - Expected per the intended scheduling contract: the wait is honest and bounded — the unchanged fact is stated once, and jobs.json is not rewritten while nothing changes; the cadence still runs so a later key save is noticed.
  - Actual: the same line and the same unchanged `jobs.json` were produced **once per 5s tick indefinitely**.
- RED command, exit, failing assertion; why this is not a setup failure:
  - `node scripts/testing/run-backend-tests.mjs --only job-cancellation-missing-key` → **exit 1**, `tests 2 / pass 1 / fail 1`, suite coverage `1/1 file(s) completed, 2 test(s) = 2 marks`.
  - Failing assertion: `AssertionError [ERR_ASSERTION]: the same waiting fact was restated 4 times` (`4 !== 1`) at `job-cancellation-missing-key.test.ts:131`.
  - Not a setup failure: the same run's no-replay control passed, the job was `running` with `isDuplicate === true`, `finished_at === null`, zero provider calls, and the record still `queued`. The four restatements are the four reconciliation passes inside a 3-interval (16s) observation window — the product cadence, measured.
- If not reproduced: n/a (reproduced).
- Current-source callers and ownership/completion boundary:
  - `reconcileCancellationJob` (`job-queue.ts:676`) is the only scheduler; `scheduleCancellationReconciliation` (`:766`) is invoked from boot recovery (`:2996`) and from the `finally` timer (`:755`).
  - The keyless branch deliberately returns **before** `claimRemoteCancellation` (`:160`) and before `reconcilePendingJobCancellation` (`job-cancellation-reconciler.ts:233`), so no cancellation claim or generation request is consumed without credentials. This is correct and was preserved.
  - Duplicate-lock/ownership is unchanged: with no key the job stays `running`, `hasUnsettledProviderWork` stays true, `isDuplicate` stays true, and `removeTerminalJob` refuses.
