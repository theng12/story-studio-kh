Relevant accepted-plan rules used for this audit:

- The customer-facing visual decision belongs to the episode; Pipeline, Jobs, Board, and assembly must consume that same choice.
- There are exactly two visual sources: Scene Plan / Continuity and Image Pool. A source choice is separate from source readiness.
- Mixed selections must show source/settings per episode, and row completion/count denominators must include only applicable requirements.
- Generated work, submitted jobs, receipts, and finished videos are preserved; a settings change cannot broaden or resubmit work.
- Existing uniform pacing remains valid; formula or format changes must not silently enable variable pacing or motion.

## Baseline static findings (maximum eight; historical)

These were reproducible from pre-change code paths and the accepted plan. Their resolved evidence is indexed below; this section itself is not a claim that the defects remain present.

### F1 — P0: Pipeline, Board, dashboard, and sidebar cannot represent mixed per-episode visual sources

**Reproduction from source:** make one episode carry an `image_pool` visual-source sidecar and another use Scene Plan, then open Pipeline or Board for the same project. `pipeline.vue:768-774` and `955-960`, `board.vue:369-382`, `layouts/dashboard.vue:178-219`, and `useProjectFlow.ts:30,46-56` each hold a single project-level `visualSource` from `/effective-format`; the type has only format values and no `image_pool`. The backend independently reads each episode's source at `pipeline.ts:430-465`, but only to special-case `video_assembly`.

**Impact:** the UI offers one chain, one set of columns, and one completion interpretation for all selected episodes. An Image Pool episode can therefore be presented with Scene Plan stages, while the backend later reads a different per-episode source. This directly violates the plan's mixed-selection and one-episode-source rules.

**Disposition:** confirm with fixture coverage in milestone 2; extend the existing source reader/flow rather than adding a second configuration system.

### F2 — P0: Pipeline “queued jobs” count is a Cartesian estimate, not the work it will queue

`frontend/pages/projects/[slug]/pipeline.vue:588-592` renders `selectedEpisodes.size * checkedStepCount` as “queued jobs”, and `2171-2174` uses the same product in the Run Batch label. The selected step set includes inline/config-only `character_sheet` (`pipeline.vue:928-938`, with the apply notice at `2323-2325`), optional stages, and stages the backend may skip or reuse after preflight. The backend returns actual `enqueued`, `reused`, `skipped`, and `total_jobs_planned` fields (`pipeline.vue:2312-2328`) only after submission.

**Impact:** a visible count can say four queued jobs for two episodes and two checked steps even when one step is applied inline, already complete, blocked, or reused. This is a data/count flaw at the primary paid-work control.

**Disposition:** replace the wording/count with a source-aware preflight result that distinguishes selected stages, eligible episodes, actual queued jobs, inline actions, and skips.

### F3 — P1: Board column denominators count inapplicable episodes

`frontend/pages/projects/[slug]/board.vue:387-395` increments each column's done count over every `episodes.value` row, and the header renders `${doneCount(col)}/${episodes.length}` at lines 185-198. Columns themselves are derived once from the project-level flow at lines 379-382. There is no per-row source/readiness or “Not used” branch.

**Reproduction from source:** mix an Image Pool episode with a Scene Plan episode. The denominator remains the total project episode count and the same Scene Plan columns are shown for both. An Image Pool row cannot contribute a meaningful Scene Plan completion result, yet it remains in the denominator.

**Impact:** Board percentages and Needs Work filtering can report incomplete work for a branch that does not apply, exactly the plan's mixed-source denominator defect.

**Disposition:** add per-episode applicability and count only applicable requirements; preserve the table layout.

### F4 — P1: Source-load failures silently fall back to a plausible but unverified visual chain

Pipeline initializes `visualSource` to `'narrated-scenes'` at `frontend/pages/projects/[slug]/pipeline.vue:768` and catches `/effective-format` failure without changing it (`772-774`). Board does the same at `frontend/pages/projects/[slug]/board.vue:369-375`; the dashboard keeps its default in `frontend/layouts/dashboard.vue:178-219`. `normalizeVisualSource()` also maps unknown values to `continuity-chain` (`frontend/composables/useProjectFlow.ts:42-56`).

**Impact:** an unavailable or malformed format response produces a normal-looking chain and lets the user inspect/select work under an assumed source. The accepted rules require the source decision to be authoritative per episode and distinguish unknown/unready from a real source. A plausible fallback is especially dangerous at Pipeline and Board because counts and selected stages derive from it.

**Disposition:** show an unavailable/unknown state and disable only source-dependent controls until the source is known; do not invent a source.

**Post-change static finding:** `parseVisualSource()` now returns `null` for an absent or unknown authoritative response. Pipeline and Board clear their local source before each guarded format read and expose `formatError`; their source-dependent stage derivations are empty until a known source arrives. Dashboard withholds the workflow ribbon and exposes the same unavailable state. **Source trace; subsequent runtime evidence is listed below.**

### F5 — P1: Shared TopActionBar status popover reports legacy `images`/`video` fields, not the visual workflow's canonical steps

The shared bar renders “images”, “audio”, “merged”, and “video” status from literal keys in `frontend/components/TopActionBar.vue:109-118`; helpers at `501-512` simply read `ep.status[key]`. The canonical flow map instead defines `scene_review` and `video_assembly` at `frontend/composables/useProjectFlow.ts:158-176`, and EpisodeSelector has source-specific handling for final video at `frontend/components/EpisodeSelector.vue:507-523`.

**Impact:** after Scene Review completes, the shared popover can still show `images ○`; a completed final assembly is represented by a generic `video` key rather than the canonical final-video status. The selection control can therefore contradict Board/Selector state and make a user believe the visual branch is missing.

**Disposition:** reuse the existing shared status map and source-aware summary in the bar; preserve the popover itself.

**Post-change static finding:** the popover now builds its rows from `STEP_STATUS_FIELD`, choosing Scene Plan + Scene Review or Image Pool from the episode’s saved source and naming `video_assembly` as Final video. The legacy `images` and `video` display aliases are absent. **Source trace; subsequent runtime evidence is listed below.**

### F6 — P1: Pipeline missing-work filters inherit the project chain and can classify Image Pool episodes as Scene Plan work

The Pipeline filter/count path derives `CORE_STEP_IDS` from `visibleSteps` (`frontend/pages/projects/[slug]/pipeline.vue:1632-1659`), computes per-step missing counts over all episodes (`1727-1738`), and checks scene status through a format-neutral switch (`1783-1809`). There is no call to `readVideoVisualSource()` or Image Pool applicability in this frontend path, while the backend's only source read is the video-assembly special case (`electron/server/routes/pipeline.ts:430-465`).

**Impact:** “missing-only”, “Missing Scene Plan”, and pending selection can include episodes whose chosen source is Image Pool. Selecting those rows can then overstate required work or send the operator into a branch that is not used for that episode.

**Disposition:** resolve source per episode before deriving filters/counts, and leave source choice separate from pool readiness.

### F7 — P2: TopActionBar retains stale episode status when the route selection is cleared

`TopActionBar.vue:347-353` updates `activeEpisode` only on the `episode-selected` event. `EpisodeSelector.vue:202-208` emits only `update:modelValue` with an empty value when `route.query.episode_id` is removed; it does not emit a null/cleared episode event. The popover at `TopActionBar.vue:109-122` therefore continues to render the previous episode's title/status after the selection has been cleared by a route change.

**Impact:** the action bar can show a previous episode as the current status while the form has no selected episode. This is a shared state display defect and can mislead the next generation action, even though the button's disabled prop is page-owned.

**Disposition:** clear the shared active snapshot when the bound episode becomes empty or the selector emits a route-driven clear; add a focused regression fixture.

**Post-change static finding:** `TopActionBar` watches its bound `episodeId` and clears a snapshot that is empty or no longer matches. This keeps the fix inside the shared bar because direct `EpisodeSelector` consumers use payload-dereferencing handlers. Focused mounted fixtures cover both clearing that bound snapshot and a reused source picker save race. **Source trace; subsequent runtime evidence is listed below.**

### F8 — P1: Image prompt-preview responses can render under a later selected episode

**Reproduction from source:** start a preview for Scene 1 or Thumbnail 1 in `frontend/pages/projects/[slug]/images.vue`, then switch episodes before `/projects/:slug/preview-image` resolves. The preview state key was only `${kind}-${number}` (`images.vue:946-948`), and `renderPromptPreview()` previously wrote its response directly into that key (`1017-1067`). The episode watcher clears that state but the pending response could restore the same row key for the newly selected episode.

**Impact:** preview artwork and its model/aspect metadata could be presented as the current episode's row even though it was rendered from the previous episode's prompt. The action is a preview only, but its displayed result can steer the next paid image choice.

**Disposition:** `renderPromptPreview()` now snapshots the existing `imageScopeSequence`, project, and episode before requesting the preview, then discards both successful and failed stale completions. The existing image workflow selection-safety fixture asserts that guard. **Source trace; subsequent runtime evidence is listed below.**
