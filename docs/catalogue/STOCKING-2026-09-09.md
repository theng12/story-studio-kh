### The origin was wrong on the first attempt, and why that matters

Recorded because it is the kind of mistake that passes every check. The first writing run
used `--preview-base-url http://127.0.0.1:8010`, taken from `STUDIO_AUTH_PUBLIC_BASE_URL`
and `VITE_API_BASE_URL` in `.env`. Both say 8010; **the API actually listens on 8000**, and
nothing listens on 8010 at all. `STUDIO_CONTENT_PREVIEW_BASE_URL` is unset, so there was no
configured value to fall back on.

The run reported success for every pack, because publishing a gallery only writes a row —
nothing fetches the URL it stores. The catalogue would have carried seventeen shop-window
images that no shopper's browser could load, and the stocker had no way to know.

The fix was a second writing run with `--preview-base-url http://127.0.0.1:8000`. The bytes
are content-addressed and were already in object storage, so only the catalogue rows changed;
the run reported "published N preview image(s)" again because the stored URLs differed.
Verified afterwards two ways: every gallery entry now carries the `127.0.0.1:8000` origin,
and one image was fetched end-to-end over the unauthenticated route —

```
GET /v1/content/previews/cprod_52cb851711d346ae9bfc9b7853edc91b/105c1260…287c1d.webp
→ 200, image/webp, 80,892 bytes
```

— which is byte-for-byte the size of the committed
`sketch-and-marker-note-1.webp`.

**Worth fixing properly rather than remembering:** set `STUDIO_CONTENT_PREVIEW_BASE_URL` in
`.env` to the origin a browser really reaches this API at, so no future run has to pass the
flag or guess. And `STUDIO_AUTH_PUBLIC_BASE_URL` / `VITE_API_BASE_URL` claiming a port
nothing serves is its own bug, upstream of this one — either a proxy is missing or those two
values are stale. Both need the owner, so neither was changed here.
