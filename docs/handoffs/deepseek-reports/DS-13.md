## What was measured and how
The queue keeps every live job and up to `MAX_PERSISTED_TERMINAL_HISTORY` (750) terminal jobs. A persistence pass serializes the project's **whole** retained history into `jobs.json` (compact `{ jobs }`), through one coalesced atomic write; the SSE routes write `event: update\ndata: ${JSON.stringify(job)}\n\n` per subscriber, and **each changed frame carries the job's whole `output_lines` array**.

The script points `STORY_STUDIO_DATA_DIR` at a fresh temp dir before importing the service modules (the customer's real Library is never opened for writing), seeds synthetic histories, then drives **real persistence passes** through `checkpointJobState()` + `_waitForJobPersistenceForTesting()` and reads the existing `_getJobPersistenceCountersForTesting()` counters. Each timing is repeated three times on a fresh project; the report uses the median.

Environment: Node v26.8.2, darwin/arm64, Apple M2 Max (12 logical cores), 32 GiB RAM.

## Finding — no observed user-impact case
- At the observed maximum (592 lines) one persistence pass is ~7 ms and one SSE frame is ~24 KiB. The largest real `jobs.json` (0.67 MiB) is written in well under 100 ms.
- The synthetic extreme (10,000 lines in one job) costs 0.56 MiB and ~21 ms per coalesced write, and 400 KiB per SSE frame per subscriber. **No real project on this Mac is within an order of magnitude of that**, and the write is already coalesced (a 200-mutation burst is one write), so the audit's "unbounded clone per record" concern is not realised in practice: cost is linear in retained history, bounded by the 750-job retention, and applied once per dirty pass.
- Therefore, per the packet's own rule, **no caps, caching, or truncation are proposed**. `output_lines` remains durable provider evidence; nothing was trimmed.
- Latent threshold recorded for the future (not a defect today): a single job's log would have to reach roughly 5,000–10,000 lines (~200–400 KiB per frame, ~0.3–0.6 MiB per write) before the SSE bytes over a remote (Tailscale) connection or the write time became worth optimising — e.g. a fingerprint-keyed delta frame instead of the whole array, or a per-job line cap that never drops durable evidence. That is a follow-up decision, not work taken here.
- Existing regression coverage already pins the invariants that keep this bounded: `job-queue-evidence-coalescing.test.ts` (`atomic_writes <= 3` for a batch) and `job-cancellation-missing-key.test.ts` (`atomic_writes === 0` for a settled job), plus `job-queue-persistence-retention.test.ts` for the 750-job terminal bound. No new test was needed for a no-change measurement; the script is re-runnable evidence.
