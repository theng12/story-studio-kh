## Reproduction and root cause
- **F-04 — entering the tab did not read the status, and a failed read claimed "not installed".**
  The FFmpeg card lives in the `maintenance` tab. `refreshFfmpegStatus()` was called only from `onMounted` (when that tab was somehow already active) and from `applyHash()` for the literal `#ffmpeg` link; the `activeTab` watcher loaded the YouTube list and the archive status for `maintenance` but **never** probed FFmpeg. Entering "Files & maintenance" by click therefore rendered the card with `ffmpegStatus === null`, where the installer's chain is `v-if="bundled-ready"` → `v-else` and `:open="!ffmpegStatus?.installed || ffmpegInstalling"` — an **expanded one-click recovery download** offered for a status the app had not read. Worse, `catch { ffmpegStatus.value = { installed: false } }` collapsed a failed check (backend unreachable, permission error, non-executable binary) into the same "Not installed" badge and install prompt, the exact AGENTS.md §6 shape.
- **F-05 — two competing writers of `category_id`; the project-meta one won the race.**
  `loadProject()` in `useProject` fetches project meta and the settings config **in parallel** and assigns each as it resolves. `category_id` lives on ProjectConfig, but `watch(project, …, { immediate: true })` reset `projectForm.category_id = undefined` on **every** `project` replacement. Whenever meta resolved after config, the hydrated category was wiped and the field fell back to "Use app default"; the next Publishing save then sent `category_id: undefined` and **persisted the silent clear**.
- **RED evidence.** The page was restored from `HEAD` (`git show HEAD:… > settings.vue`) and the new tests run against it: **tests 4, pass 1, fail 3, exit 1** — the three new assertions (category hydration on mount, FFmpeg tab probe, installer gating). Files restored byte-identically afterwards: sha256 `3c5238aa9a7028353c9f2b8357dd1cdb240581c125d595509d5be484bf341b5f` before and after; the `HEAD` content hashed `4dcb744b…`.

## Change and proof
- **F-04:** `ffmpegStatusError` is a new explicit state; the catch sets `ffmpegStatus.value = null` (unknown) and retains `e.data.detail || e.message`, instead of fabricating `{ installed: false }`. The card gained a `role="alert"` failure block with **Retry check**. The installer is now `v-else-if="ffmpegStatus"` with an unknown-state placeholder `v-else`, and the manual-install fallback requires a real status (`v-if="ffmpegStatus && ffmpegStatus.source !== 'bundled'"`), so no repair action is offered for a status that was never read. The `activeTab` watcher probes `/ffmpeg/status` on entering `maintenance` while the answer is unknown (and not already in flight); a known status is left to the explicit "Re-check status" button.
- **F-05:** the project-meta watcher no longer touches `category_id`. The per-project reset moved to `watch(slug, …)` — the only event that actually means a different project is on screen — which now blanks **both** `category_id` and `mark_as_ai_generated`; the config watcher rehydrates them from that project's own config, and a failed/empty config read leaves them blank rather than showing the previous project's answer (AGENTS.md §4). A same-project meta refresh therefore preserves both the hydrated value and an unsaved deliberate change.
