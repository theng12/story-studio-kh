## The caller chain, traced
1. **Recorded at generation time.** `generateAudio()` parses the narration script (`parseNarrationDocx`), then — in this order — swaps in expression-tagged text (`req.use_expression`), normalizes (`normalizeSectionsForTts`), appends auto-pacing tags (`req.fish_autopace`), selects sections, generates, and finally writes provenance with `normalized_script_hash: update.scriptHash` (`generators/audio.ts`, around the `updates.push(...)` in the provenance block; persisted by `audio-quality-store.ts`).
2. **Recomputed at check time.** `inspectChapterQuality()` (`services/audio-quality.ts`) calls `currentScriptHash()` → `currentChapterScriptHash()`, which reads the script file (`currentScript()` → `parseNarrationDocx`, exact file first then the unified `*_script_narration.*`) and hashes `normalizeForTts(text).text`.
3. **Compared.** `if (!scriptHash || scriptHash !== saved.normalized_script_hash)` marks the chapter stale and reports `current_script_hash` / `saved_script_hash` in the review row.
4. **Also written on the refresh path.** `generators/audio-merge.ts` records `normalized_script_hash: scriptHash` from `currentChapterScriptHash()` after a local post-promotion refresh, so the merge path already used the recomputed form.

## The defect
The two sides hashed **different text**.

- The recorded side hashed `section.text` **after** the run had transformed it: expression markup had replaced the spoken text, normalization had run, and auto-pacing had appended pause tags.
- The recomputed side always hashes the **script file**, normalized, with no tags.

So on any run with **expression markup or auto-pacing enabled**, the recorded hash could never equal the recomputed one, and the quality check told the customer the script had changed while it had not — a false invalidation, exactly the case X-01 names. The generator's own comment already conceded the mismatch ("normalizeForTts leaves square brackets untouched"), and `audio-merge.ts` had been using the recomputed form for the same field.

Measured, on one sentence with auto-pacing on:

```
submitted text differs from script text : true
HEAD recorded                            : sha256:4bb06c571181f700   (paced text)
check recomputes                         : sha256:54e1d39b0f8a0c69   (script text)
HEAD reports "script changed"            : true   ← the defect
FIX  recorded                            : sha256:54e1d39b0f8a0c69
FIX  matches the recomputation           : true
```

## The fix
One rule: **the durable fingerprint describes the script on disk, never the run.**

- `chapterScriptFingerprint(rawSectionText)` is the single implementation, and `currentChapterScriptHash()` is defined in terms of it — so the two sides cannot drift apart again.
- `generators/audio.ts` captures a `slug → fingerprint` map **immediately after parsing** and before the expression, normalization and pacing steps, then records from that map. The fallback (`?? chapterScriptFingerprint(section.text)`) keeps the record well-formed if a section somehow misses the map.
- No contract changed: the stored field name, the comparison, the review codes and the refresh path are all as they were. Only *which bytes* are hashed changed, and only on the recorded side.

## Proof
- **Behavioural round trip:** a real script file is parsed, `currentChapterScriptHash()` recomputes it, and it equals the captured fingerprint.
- **Equivalent normalization:** normalizing twice is idempotent for the fixture, and `chapterScriptFingerprint(normalized) === chapterScriptFingerprint(raw)` — a benign normalization cannot invent a difference.
- **The false positive is pinned:** auto-pacing and expression markup both change the submitted text (`paced !== normalized` asserted, so the test cannot pass vacuously) while the fingerprint still matches the recomputation.
- **The true positive survives:** rewriting the script file changes the recomputed fingerprint.
- **Wiring is pinned too:** the capture must sit before the expression, normalization and pacing steps, and the provenance record must read from the map — the two assertions that fail if someone reintroduces `hashInput(section.text)`.
